# 调试记录：从空工程到双通道示波器

本文按时间顺序记录把这套示波器跑起来过程中踩到的 9 个坑，每条包含 **现象 / 根因 / 修复**。所有引用的源码路径都是仓库内的相对路径。

---

## 0. 起点状态

- 工程 `Project/Oscilloscope.uvprojx` 定义了 `USE_HAL_DRIVER, STM32F103xE`，主要 BSP（lcd / button / uart / delay 等）已是 HAL 风格
- 但 `User/main.c`、`Drivers/{Inc,Src}/adc_sample.{h,c}`、`Drivers/Inc/oscilloscope.h` 是**标准外设库（SPL）风格**，留着 `#include "stm32f10x.h"`
- README 描述的 `User/inc + User/src` 目录结构与现状不符；按键 API 也写的是不存在的 `Key_Scan / KEY0..KEY4 / KEY_NONE`

**直接编译完全失败**——以下是逐个坑的修复过程。

---

## 1. SPL 与 HAL 头文件冲突

**现象**
```
adc_sample.c: error: call to undeclared function 'DMA_GetITStatus'
adc_sample.c: error: use of undeclared identifier 'DMA1_IT_TC1'
adc_sample.c: error: unknown type name 'GPIO_InitTypeDef'; did you mean 'GPIO_TypeDef'?
...
stm32f103xe.h: error: redefinition of enumerator 'NonMaskableInt_IRQn'
stm32f103xe.h: error: redefinition of enumerator 'EXTI0_IRQn'
...（4 warnings and 20 errors generated.）
```

**根因**

工程整体走 HAL，但下列文件还停留在 SPL：
- `User/main.c`：`#include "stm32f10x.h"` + `NVIC_PriorityGroupConfig` 等 SPL API
- `Drivers/Inc/adc_sample.h`、`Drivers/Src/adc_sample.c`：`GPIO_InitTypeDef / ADC_InitTypeDef / DMA_InitTypeDef / TIM_TimeBaseInitTypeDef / NVIC_InitTypeDef` + `RCC_APB2PeriphClockCmd` + `DMA_GetITStatus` 等
- `Drivers/Inc/oscilloscope.h`：`#include "stm32f10x.h"`

当 `lcd.h`（包含 `stm32f1xx.h`，HAL）和 `adc_sample.h`（包含 `stm32f10x.h`，SPL）在同一翻译单元相遇，两者都定义了 `__CM3_REV`、`IRQn_Type` 枚举等 → 重定义。

**修复**

全面切到 HAL：
- 头文件 `stm32f10x.h` → `stm32f1xx.h`
- 重写 `adc_sample.c` 用 `ADC_HandleTypeDef / DMA_HandleTypeDef / TIM_HandleTypeDef` + `HAL_ADC_Init / HAL_DMA_Init / HAL_TIM_Base_Init` + `HAL_ADC_Start_DMA`
- `RCC_APB2PeriphClockCmd(RCC_APB2Periph_ADC1, ENABLE)` → `__HAL_RCC_ADC1_CLK_ENABLE()`
- ADC 完成中断从 `DMA_GetITStatus(DMA1_IT_TC1)` 改为 `HAL_DMA_IRQHandler(&hdma_adc1)` → 由 HAL 派发到 `HAL_ADC_ConvCpltCallback`
- `main.c` 用 `HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_2)` 替代 `NVIC_PriorityGroupConfig`

## 2. 按键模块 API 不匹配

**现象**

编译 `main.c` 报：`Key_Scan / Key_Init / KEY0 / KEY_NONE` 全部 undeclared。

**根因**

`main.c` 沿用了 README 假设的 API，但仓库实际实现完全不同：

| README 假设 | 仓库实际（`Drivers/{Inc,Src}/button.{h,c}`） |
|------------|------------------------------------------|
| `Key_Init()` | `button_init()` |
| `Key_Scan(0)` | `button_scan(uint8_t mode)` |
| 枚举 `KEY0..KEY4 / KEY_NONE` | 宏 `KEY0..KEY2 / WK_UP`（是 `HAL_GPIO_ReadPin` 表达式，不是按键码） |
| 返回值 `KEY0..KEY4` | 返回值 `KEY0_PRES / KEY1_PRES / KEY2_PRES / WKUP_PRES`，无按下时返回 0 |

而且实际硬件只有 KEY0(PE4) / KEY1(PE3) / KEY2(PE2) 三个键能用：WK_UP 的 PA0 已被 ADC1_IN0 占用。

**修复**

`main.c` 改为三键方案，功能合并：

```c
case KEY0_PRES: /* 时基切换 */
case KEY1_PRES: /* 量程切换 */
case KEY2_PRES: /* Run / Stop */
```

触发电平 +/- 和 SINGLE 模式 UI 入口去掉，触发电平固定 1.65V（代码层面的 NORM/SING 通过改 `g_osc.trig_mode` 仍可启用）。

## 3. LCD API 命名与签名不匹配

**现象**

编译 `oscilloscope.c` 出现一长串 `LCD_Fill / LCD_ShowString / LCD_ShowFloat / LCD_Init / ORANGE / LIGHT_GRAY / DARK_GRAY` undeclared 错误。

**根因**

`oscilloscope.c` 调的 API 命名是另一个 LCD 库的（驼峰 + 大写宏），而仓库实际是小写 `lcd_*` 命名空间：

| 调用错的 | 实际 API |
|---------|---------|
| `LCD_Init()` | `lcd_init(void)` |
| `LCD_Fill(sx,sy,ex,ey,color)` | `lcd_fill(uint16_t sx, uint16_t sy, uint16_t ex, uint16_t ey, uint32_t color)` |
| `LCD_ShowString(x,y,str,fc,bc,size)` | `lcd_show_string(x, y, width, height, size, char *p, color)` — **背景色取自全局 `g_back_color`**，无 bc 参数 |
| `LCD_ShowFloat(...)` | 不存在；只有 `lcd_show_num`，不支持浮点 |
| `ORANGE / LIGHT_GRAY / DARK_GRAY` | 不存在；只有 `BROWN / BRRED / GRAY / LGRAY / DARKBLUE` 等 |

外加两处签名误用（这两个**编译能过但行为错误**）：
- `lcd_draw_line(x, y, len, color)` — 实际签名是 `(x1, y1, x2, y2, color)`，原代码把"长度"当 y2 用 → 画一条端点错位的斜线
- `lcd_draw_rectangle(x, y, width, height, color)` — 实际签名是 `(x1, y1, x2, y2, color)`，宽高被当成右下角坐标

**修复**

在 `oscilloscope.c` 文件顶部加：
- 颜色映射：`#define ORANGE 0xFD20`、`#define LIGHT_GRAY LGRAY`、`#define DARK_GRAY GRAY`
- 包装函数 `osc_show_str` / `osc_show_float`：前者临时改写 `g_back_color` 调 `lcd_show_string`；后者手动 ASCII 转换避免引入 stdio
- 4 参数 `lcd_draw_line` 想画水平线的地方改 `lcd_draw_hline`；竖线展开成 5 参 `lcd_draw_line`
- `lcd_draw_rectangle` 调用全部改为 `(x, y, x+w-1, y+h-1, color)`

## 5. 烧录后 LCD 全屏白色 + 按键无反应

**现象**

烧录到板子，上电后 LCD 一直白色（上电默认状态），按键无任何响应。

**根因**

`Drivers/Src/lcd.c:418` 内部：
```c
lcd_write_reg(0x0000, 0x0001);
delay_ms(50);
lcddev.id = lcd_read_reg(0x0000);
u1_printf("LCD ID:%x\r\n", lcddev.id);   /* ← 关键：UART1 打印 */

if (lcddev.id == 0X9325) {
    lcd_ex_ili9325_reginit();
}
lcd_display_dir(0);
LCD_BL(0);
lcd_clear(WHITE);
```

而 `main.c` 在调 `lcd_init` 前**没有调 `u1_init`**。`u1_printf` 内部通过未初始化的 `uart1.uart` 句柄调 `HAL_UART_Transmit` → 阻塞或访问异常 → 程序卡死。结果 `lcd_ex_ili9325_reginit()` 和 `lcd_clear(WHITE)` 都没执行，LCD 停在上电默认白屏。

**修复**

`main.c` 在 `lcd_init` 之前加：
```c
u1_init(115200);                   /* lcd_init 内部会用 u1_printf 打印 LCD ID */
lcd_init();
```

上电时可在串口看到 `LCD ID:9325`，确认握手成功。

## 6. HAL_GetTick 冻结（潜在超时卡死）

**现象**

第 5 节修完后界面起来了。但仔细审一遍代码发现一个隐患：`Wait_Sample_Done` 用 `HAL_GetTick()` 算超时，可能永远不超时。

**根因**

`Drivers/Src/delay.c:24` 的 `delay_init` 在非 OS 模式下做的事：
```c
SysTick->CTRL = 0;     /* 清掉 SysTick，包括中断使能 */
HAL_SYSTICK_CLKSourceConfig(SYSTICK_CLKSOURCE_HCLK_DIV8);
fac_us = sysclk / 8;
```

然后 `delay_us` 用 SysTick 的**单次倒数模式**驱动延时——每次调用都重写 LOAD/VAL/CTRL。

副作用：**SysTick 中断被关闭**，HAL 的 `uwTick` 不再自增，`HAL_GetTick()` 永远返回固定值。

`Wait_Sample_Done` 内 `(HAL_GetTick() - start) >= timeout_ms` 永远为假——只要 ADC 因为任何原因没置位 `g_sample_done`（比如 PA0 悬空导致触发不出来），主循环就死等。

**修复**

`main.c:70` 改用 `delay_ms(1)` 自累计计时：
```c
static uint8_t Wait_Sample_Done(uint32_t timeout_ms)
{
    uint32_t elapsed = 0;
    while (!g_sample_done) {
        uint8_t k = button_scan(0);
        if (k) Handle_Key(k);
        delay_ms(1);
        if (++elapsed >= timeout_ms) return 0;
    }
    return 1;
}
```

同时把主循环里 `HAL_Delay(50)` 也换成 `delay_ms(50)`，全链路统一。

## 7. 屏幕一闪一闪

**现象**

界面起来后能用，但快时基档下整个屏幕在闪烁（高频黑闪），慢档（200ms/div）反而稳定。

**根因**

每帧绘制都做了**全片擦除 + 重画**：
- 波形：`lcd_fill(波形区, BLACK)` + `Osc_DrawGrid()` 整张网格
- 状态栏：`lcd_fill(0, 0, 319, 15, BLACK)` + 全部文字重画
- 信息栏：`lcd_fill(整个右栏, BLACK)` + 标签 + 数值 + 按键提示全部重画

快时基档（500µs/div）一帧采样 0.5ms，主循环每秒可能上百帧——肉眼就是闪。

**修复**

改为增量绘制：

1. **波形**：缓存 `s_prev_ys1[240]`、`s_prev_ys2[240]`，每帧"用黑色擦上一帧线 → 画新线"
2. **网格**：只在 `Osc_Init` 画一次，**不再每帧重画**（副作用：擦除路径会啃掉路径上的网格点，视觉上能容忍）
3. **触发线**：缓存 `s_prev_trig_y`，y 未变只重画一次（补回被波形擦除路径啃掉的虚线像素），y 变化先擦旧再画新
4. **信息栏**：拆为 `Osc_DrawInfoBarLabels()`（标签 + 三键提示，只画一次）+ `Osc_UpdateInfoBar()`（仅 `lcd_fill` 数值字段那一小条 50px×12px，再写新值）
5. **状态栏**：从主循环里删掉 `Osc_UpdateStatusBar()`，只在 `Handle_Key` 内调
6. **量程切换（KEY1）** 后调 `Osc_InvalidateWave()` 让 `s_prev_ys` 失效 + `Osc_DrawTrigLine()` 重画触发线

## 8. 双 ADC 启动后 CH2 永远是 0V（坑 #1：slave EXTTRIG 未置位）

**现象**

`ADC1+ADC2 dual REGSIMULT` 模式启用后，CH2（PA1）波形一直贴在屏幕底部，无论 PA1 接 3.3V 还是 GND 都不变；CH1 工作正常。

**根因**

详细对照 STM32F1xx HAL ADC Ex 源码后，发现 F1 HAL 一个长期 bug：

1. `STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_adc.c:503` 注释明确写："External trigger polarity (ADC_CR2_EXTTRIG) is set into HAL_ADC_Start_xxx functions" —— **`HAL_ADC_Init` 不写 EXTTRIG 位**
2. `stm32f1xx_hal_adc_ex.c:692-693` 注释又说："External trigger of ADC slave must be enabled, it is already done into function HAL_ADC_Init()" —— 这句和第 1 条**自相矛盾**
3. 实际看 `HAL_ADCEx_MultiModeStart_DMA` 的代码（770、775 行），它只为 **master**（hadc->Instance 指 ADC1）设 EXTTRIG，**不会为 slave (ADC2) 设**

结果：**ADC2 的 `CR2.EXTTRIG` 永远是 0**，dual mode 下 master 的硬件同步触发链路到不了 slave，slave 不转换，DR 高 16 位永远 0。

**修复**

`adc_sample.c:136` 在 `Calibration_Start` 之后手动补一刀：
```c
HAL_ADCEx_Calibration_Start(&hadc1);
HAL_ADCEx_Calibration_Start(&hadc2);

/* F1 HAL 已知坑：HAL_ADC_Init 不写 CR2.EXTTRIG，
 * HAL_ADCEx_MultiModeStart_DMA 也只为 master 写，slave 永远 0。
 * 参考 RM0008 §11.12.3 ADC_CR2.EXTTRIG */
SET_BIT(hadc2.Instance->CR2, ADC_CR2_EXTTRIG);
```

EXTTRIG 在 ADC enabled 时也可写（RM0008 无禁止）；位一旦置位，HAL 后续路径不会清它（`MultiModeStop_DMA` 只动 ADC1 的 CR2，不动 ADC2 的）。

## 9. 第一次正确、第二次起 CH2 失效（坑 #2：stop 清掉 DUALMOD）

**现象**

补上 EXTTRIG 之后，**复位瞬间** CH2 短暂正确显示（PA1=3.3V 时青线贴顶），**但很快塌底**与 CH1 重合，之后不再响应。

**根因**

`stm32f1xx_hal_adc_ex.c:838-841`，`HAL_ADCEx_MultiModeStop_DMA` 在每次停止时做：
```c
/* Disable ADC DMA mode */
CLEAR_BIT(hadc->Instance->CR2, ADC_CR2_DMA);

/* Reset configuration of ADC DMA continuous request for dual mode */
CLEAR_BIT(hadc->Instance->CR1, ADC_CR1_DUALMOD);   /* ← 这一刀 */
```

**每次 stop 都把 DUALMOD 清成 0（独立模式）**。流程拆开看就是：

1. 上电 init：`HAL_ADCEx_MultiModeConfigChannel` 设 DUALMOD=REGSIMULT
2. 第一次 `ADC_Sample_Start` → 同步采样正常 → 屏幕上看到 CH2 正确
3. DMA 完成回调内 `HAL_ADCEx_MultiModeStop_DMA` → **DUALMOD 被清零**
4. 第二次 `ADC_Sample_Start` → `HAL_ADCEx_MultiModeStart_DMA` 不会重新设 DUALMOD → 退化为独立模式 → ADC1 的 DR 高 16 位变成 0 → CH2 永远显示 0V

而 `HAL_ADCEx_MultiModeStart_DMA` 内部并不重新写 DUALMOD —— HAL 假定它是"设一次终身有效"的配置位，自家 `MultiModeStop_DMA` 又顺手把它清了，逻辑矛盾。

**修复**

`adc_sample.c:178` 在 `ADC_Sample_Start` 顶部把 DUALMOD 写回（此时两个 ADC 都 disabled，写位合法 RM0008 §11.12.2）：

```c
void ADC_Sample_Start(void)
{
    g_sample_done = 0;

    /* HAL F1 bug: MultiModeStop_DMA 清掉了 DUALMOD，每次启动前写回。 */
    MODIFY_REG(hadc1.Instance->CR1, ADC_CR1_DUALMOD, ADC_DUALMODE_REGSIMULT);

    HAL_ADCEx_MultiModeStart_DMA(&hadc1, g_adc_buf, SAMPLE_BUF_SIZE);
    __HAL_TIM_SET_COUNTER(&htim3, 0);
    HAL_TIM_Base_Start(&htim3);
}
```

至此双通道同步采样持续稳定工作。

## 附：F103 双 ADC dual REGSIMULT 完整启用要点清单

未来如果要在别处复用 F1 HAL 的 dual ADC 同步模式，下面这套至少要做：

1. **两个 ADC 各自 `HAL_ADC_Init` + `HAL_ADC_ConfigChannel`**
2. **master (ADC1) 用真正的外部触发**（如 `ADC_EXTERNALTRIGCONV_T3_TRGO`）；**slave (ADC2) 用 `ADC_SOFTWARE_START`**（否则 `HAL_ADCEx_MultiModeStart_DMA` 第 694 行的 `ADC_IS_SOFTWARE_START_REGULAR(slave)` 检查会失败返回 `HAL_ERROR`）
3. `HAL_ADCEx_MultiModeConfigChannel(&hadc1, &multimode)` 在两个 ADC 都 disable 时调（first time set DUALMOD）
4. **两个 ADC 都校准** `HAL_ADCEx_Calibration_Start`
5. **手动 SET_BIT(ADC2->CR2, ADC_CR2_EXTTRIG)**（一次即可，HAL 不会清它）
6. **每次 `ADC_Sample_Start` 之前手动写回 DUALMOD**（HAL 会在每次 stop 时清）
7. DMA 配 WORD/WORD 对齐（双重模式下 ADC1->DR 是 32-bit：低 16 位 ADC1，高 16 位 ADC2）
8. 启动用 `HAL_ADCEx_MultiModeStart_DMA(&hadc1, (uint32_t*)buf, len)`；停止用 `HAL_ADCEx_MultiModeStop_DMA(&hadc1)`
9. 完成回调依然走 `HAL_ADC_ConvCpltCallback`（DMA TC → HAL 派发）

第 5 和第 6 条是 HAL 本身的两个相关 bug，**STM32CubeF1 官方例程 `ADC_RegSimul_DualMode` 在不少版本里都有同样毛病**，需要应用层自己补救。
